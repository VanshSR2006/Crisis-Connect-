# Merge Conflict Risk Report — Crisis Connect

> This report identifies files and areas that carry the highest risk of merge conflicts
> when five members work in parallel.
> **"If two members need the same file, stop and coordinate before editing it."**

---

## HIGH RISK

### 1. `backend/app/main.py`
**Owner:** Member 3

**Why HIGH risk:**
- This single file contains ALL backend endpoints (incidents, dispatches, resources, zones, risk calculation, WebSocket, etc.).
- Member 3 adds/modifies endpoints.
- Member 4 may want new risk endpoints added.
- Member 5 may want new optimization and simulation endpoints mounted.
- Members 1/2 may notice backend bugs and want quick fixes.
- The file is heavily edited by at least 3 workstreams' feature requirements.

**Mitigation:**
- Members 4 and 5 must **not** directly edit `main.py`. They implement service functions; Member 3 adds the endpoint wiring.
- New router modules (e.g., `routers/optimization.py`, `routers/simulation.py`) should be added to reduce concentration in `main.py`.
- Member 3 should prioritize splitting inline endpoints into dedicated router files.

---

### 2. `backend/app/models.py`
**Owner:** Member 3

**Why HIGH risk:**
- All SQLAlchemy ORM models (13 tables) live in one file.
- Member 3 owns it, but Members 4 and 5 frequently need new model fields (e.g., `rainfall_mm` on `RiskScore`, new `DemandForecast` fields, optimization-specific fields).
- Any team member who needs to store new data will request changes here.
- Model changes may cascade to migrations and break other members' running databases.

**Mitigation:**
- All model change requests go through Member 3.
- Changes must be announced so all members restart their local DB or run migrations.
- Consider splitting into multiple model files (e.g., `models/core.py`, `models/intelligence.py`) in a future refactor — but **do not do this without a team discussion** as it changes all import paths.

---

### 3. `src/types/index.ts`
**Owner:** Member 3

**Why HIGH risk:**
- All shared TypeScript types for the entire frontend live here.
- Members 1, 2, and 3 all import from this file.
- Member 4/5 may require new type additions as their backend response shapes evolve.
- A field rename in this file (e.g., `zone_id` → `zoneId`) breaks all consumers immediately.

**Mitigation:**
- Only Member 3 merges changes to this file.
- Frontend members 1 and 2 request type additions via PR or team message — they don't edit it directly without coordination.
- Type changes that rename existing fields must be announced to all frontend members.

---

### 4. `src/app/router.tsx`
**Owner:** Member 2

**Why HIGH risk:**
- All frontend routes are centralized in one file.
- Member 1 needs new citizen/volunteer routes.
- Member 2 needs new officer routes.
- Member 3 may need new auth routes.
- Every new page added by any team member requires a route entry here.

**Mitigation:**
- Member 2 owns and maintains this file.
- Members 1 and 3 request route additions via PR — they do not edit this file directly.
- Alternatively, consider route grouping modules in a future refactor (low priority).

---

### 5. `src/i18n/locales/en.json` (and `hi.json`, `ka.json`)
**Owner:** Member 1

**Why HIGH risk:**
- All UI strings for all three roles (citizen, officer, volunteer) live in these JSON files.
- Members 1 (citizen/volunteer strings) and 2 (officer strings) both actively add keys.
- Member 3 may add auth strings.
- JSON is line-based and Git cannot merge JSON objects intelligently — the same key added in two different branches often creates hard merge conflicts.

**Mitigation:**
- Member 1 is the primary owner and conflict resolver.
- Each member should add their own translation keys in a clearly separated section of the JSON (by role prefix, e.g., `citizen.*`, `officer.*`, `volunteer.*`, `auth.*`).
- Never reorder or restructure the JSON file — only append.
- Coordinate locale file changes via the team channel before merging.

---

### 6. `src/mocks/index.ts`
**Owner:** Member 3

**Why HIGH risk:**
- Every mock data file exports through this barrel file.
- Multiple members add mock data files and need to add their exports here.
- Adding lines to this file from multiple branches causes near-certain merge conflicts.

**Mitigation:**
- Member 3 merges all additions.
- Each member adds their own mock data file and asks Member 3 to add the export to the barrel, or submits a small PR touching only `mocks/index.ts`.

## MEDIUM RISK

### 7. `src/lib/officerContext.tsx`
**Owner:** Member 2

**Why MEDIUM risk:**
- The officer context holds state for incidents, dispatches, resources, and risk scores.
- As Member 2 adds new officer features, this file grows.
- Member 3 may want to wire real API calls into it.
- Member 5 may want to add site-ranking result state here.
- Concurrent edits from 2-3 directions are plausible.

**Mitigation:** Member 2 owns it; others request additions via PR or discussion.

---

### 8. `src/lib/citizenContext.tsx`
**Owner:** Member 1

**Why MEDIUM risk:**
- Member 1 primarily owns it, but Member 3 may need to wire real API calls to incident submission.
- The offline queue integration may require coordination between Member 1 and Member 3.

**Mitigation:** Member 1 owns it; Member 3 coordinates on API integration points.

---

### 9. `package.json`
**Owner:** Member 2

**Why MEDIUM risk:**
- Multiple members may add npm packages simultaneously (Leaflet for M2, react-query enhancements for M1/M3, etc.).
- Parallel additions to `dependencies` / `devDependencies` frequently cause merge conflicts.

**Mitigation:**
- Announce dependency additions in the team channel before adding.
- Member 2 reviews and squash-merges dependency PRs to maintain a consistent package lock.
- **Never edit `package-lock.json` manually.**

---

### 10. `backend/requirements.txt`
**Owner:** Member 3

**Why MEDIUM risk:**
- Member 4 will add ML/data packages (scikit-learn, pandas, etc.).
- Member 5 may add optimization packages (scipy, PuLP, etc.).
- Simultaneous additions by different members in different branches cause conflicts.

**Mitigation:** Announce additions in the team channel; Member 3 merges.

---

### 11. `src/lib/api/client.ts`
**Owner:** Member 3

**Why MEDIUM risk:**
- Members 1 and 2 both use this file for all API calls.
- As authentication is implemented, the token/header logic in this file will change.
- Any enhancement to error handling or retry logic affects all consumers.

**Mitigation:** Member 3 owns it; others raise issues and wait for Member 3 to fix the base client.

---

### 12. `backend/app/routers/demo.py`
**Owner:** Member 5

**Why MEDIUM risk:**
- The demo scenario seeds data across all models (User, Zone, Incident, RescueSite, Resource, RiskScore).
- As new models are added (e.g., DemandForecast, PopulationProfile seeding), Member 5 needs to add seed entries.
- This may conflict with Member 3's model changes.

**Mitigation:** Member 5 and Member 3 coordinate before model additions that affect demo seeding.
